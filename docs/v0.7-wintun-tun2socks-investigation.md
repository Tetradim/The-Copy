# v0.7 Wintun + tun2socks investigation

This note captures the full-laptop-routing research added after v0.6.1. It is a design artifact only; v0.6.1 ships no Wintun driver, no route changes, no DNS changes, and no tun2socks binary.

## Findings

- Wintun is the preferred Windows Layer-3 TUN target for a clean-room full-routing mode.
- The desktop app should remain unelevated. A small Windows service should own adapter creation, route/DNS changes, tun2socks lifecycle, and crash recovery.
- A tun2socks-style Go engine is the best short path because it already handles TUN packets and proxy forwarding patterns.
- TetherBridge still needs a stronger local SOCKS5 endpoint before full-routing can be cleanly wired. HTTP CONNECT alone is not enough for full laptop routing, DNS, UDP, or QUIC.

## Proposed integration path

1. Add `FullTunnelService` project.
2. Add official `wintun.dll` loading or a thin wrapper.
3. Add route/DNS/proxy snapshot classes.
4. Add SOCKS5 support to local relay and Android bridge.
5. Launch/manage tun2socks from the service.
6. Add route protection for the phone transport.
7. Add full restore on disconnect/crash/reboot.

## Deferred from v0.6.1

- No Wintun adapter creation.
- No tun2socks binary bundling.
- No admin service.
- No kill switch.
- No DNS or route mutation.
