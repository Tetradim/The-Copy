# v0.7 Full Tunnel Investigation: Wintun + tun2socks

This document records the v0.7+ investigation only. It is intentionally not wired into v0.6.1 UI.

## Proposed architecture

```text
Windows apps
  -> Wintun Layer-3 adapter
  -> tun2socks userspace TCP/IP stack
  -> SOCKS5 local relay at 127.0.0.1:10810
  -> USB/Wi-Fi/PAN phone transport
  -> Android bridge internet path
```

## Integration shape

- Add `TetherBridge.FullTunnel.Service`, an elevated .NET service.
- Keep `TetherBridge.Desktop` unelevated and use IPC for start/stop/status.
- Bundle only reviewed third-party components with explicit license notices.
- Treat Wintun/tun2socks as optional advanced dependencies, not requirements for proxy mode.
- Preserve a crash-recovery snapshot before every adapter/route/DNS/WinHTTP/WinINet change.

## Start sequence

1. Verify Android bridge and local relay health.
2. Ensure local relay exposes SOCKS5, not only HTTP CONNECT.
3. Create/open Wintun adapter.
4. Assign tunnel address and DNS policy.
5. Add host route for the phone transport outside the tunnel.
6. Start tun2socks with `socks5://127.0.0.1:10810`.
7. Switch default routes to the Wintun adapter.
8. Start monitors and status counters.

## Stop/recovery sequence

1. Stop accepting new full-tunnel sessions.
2. Restore routes and DNS.
3. Stop tun2socks.
4. Close Wintun session and remove/disable adapter if appropriate.
5. Restore WinINet/WinHTTP state.
6. Clear crash-recovery marker only after all restore steps succeed.

## Open engineering risks

- Admin prompts and installer trust/reputation.
- Route/DNS restore after crash or sleep/resume.
- UDP and QUIC behavior.
- IPv6 default route handling.
- Interaction with existing VPNs, endpoint security, and enterprise proxy policy.
